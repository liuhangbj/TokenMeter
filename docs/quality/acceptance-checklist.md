# TokenMeter 最终验收清单

最终验收采用"真实 App 黑盒操作为主、终端灰盒取证为辅"的机制。验收 Agent
站在最终用户角度：不看实现讲解，只拿原始需求和任务契约，像真实用户一样
点开 App、接账号、拖悬浮球、换主题。验收结论来自真实 App 行为，不来自
阅读源码或主开发 Agent 的完成说明。

## 1. 验收工作机制

### 黑盒操作

验收 Agent 操作实际安装并运行的 App（菜单栏点击、面板内点击 / 输入 /
滚动、悬浮球拖动、右键菜单、系统设置联动）。涉及 Windows 时使用 Windows
实机或等效验证环境；未经 Windows 实机冒烟的 Windows 相关功能不得判定
`PASS`（标 `BLOCKED` 并说明）。

验收 Agent 首先只取得：

- 原始用户需求；
- 已确认的任务质量契约；
- 本轮适用的模块回归清单；
- App 绝对路径、版本号和提交 SHA；
- 隔离数据目录、测试账号以及禁止执行的操作。

不得用"源码里存在这个按钮 / 调用"替代真实点击结果。

### 灰盒取证

终端和只读工具只用于确认：

- 运行进程确实来自本轮 App（`pgrep -fl tokenmeter` 核对二进制路径）；
- Info.plist 版本号与目标版本一致；
- 日志、隔离数据目录中的设置文件与界面结果一致；
- 卡死、崩溃、超时和错误归因有客观证据。

复现失败后可以有限查看源码以提供更精确的位置，但这属于辅助定位，
不构成通过证据，也不得修改文件。

### 人工边界

OAuth 扫码 / 浏览器授权的最终确认、系统钥匙串弹窗、真实付费、真实删除
账号和真实发布不得擅自执行。缺少用户配合时标记 `BLOCKED`，说明所需动作、
已经完成的替代验证和残余风险。

### 可用调试钩子

- `TOKENMETER_AUTO_PANEL=1`：启动即显示面板并进入添加供应商视图（UI 验收用）。
- `TOKENMETER_AUTO_ORB=1`：启动即显示悬浮球。
- `TOKENMETER_DATA_DIR=<路径>`：隔离数据目录（不动真实凭证与设置）。
- `TOKENMETER_LOG_FILE=<路径>`：日志输出到文件。
- `dev-deploy.sh --isolate`：等效的隔离部署。

## 2. 进入验收的前置条件

- [ ] 原始需求和任务质量契约已经固定。
- [ ] 独立技术审核已通过，或明确列出允许带入验收的非阻断问题。
- [ ] 主开发 Agent 已完成 `tsc`、`cargo test` 和 `dev-deploy.sh` 本机实测。
- [ ] 已提供正确 App 的绝对路径、版本号和提交 SHA。
- [ ] 已说明隔离数据目录、测试账号和平台登录态要求。
- [ ] 已列出真实数据中禁止修改、删除或触发的范围。
- [ ] 已关闭旧实例（单实例锁会互相干扰），并能确认当前实例路径。
- [ ] 验收前已记录仓库状态和 App 初始状态。

任何一项缺失都不得用默认假设填补。可以先执行不受影响的项目，但最终结论
标记为 `BLOCKED` 或限定范围通过。

## 3. 版本与运行真实性

- [ ] 运行进程路径来自本轮部署的 App，不是旧实例残留。
- [ ] 设置面板中显示的版本号与目标版本一致。
- [ ] 重启 App 后仍启动同一版本。
- [ ] 需要发布验收时：从 GitHub Releases 下载真实产物，核对架构
  （aarch64 / x64）、安装、启动和核心功能。

## 4. 功能主路径

- [ ] 从真实入口开始：点托盘图标开面板，不绕过任何前置步骤。
- [ ] 面板显示各账户主值、进度条、余额、重置倒计时、套餐徽章、健康点。
- [ ] 添加供应商向导：厂商分组展开 / 收起、单类型直接进表单、OAuth /
  API Key / 本机凭证导入三种路径可达（真实授权走不通时标 BLOCKED）。
- [ ] 刷新：打开面板立即刷新；手动刷新按钮工作；"更新于 X 前"时间戳变化。
- [ ] 账户管理：排序上移下移、昵称设置与清除、移除确认流程完整。
- [ ] 设置：主题 × 外观切换即时生效、刷新间隔修改生效、开机启动开关生效。
- [ ] 悬浮球：大球展开、小球收起、拖动、边缘吸附、隐藏与从设置恢复。
- [ ] 自动更新：检测 → 下载 → 提示 → 用户确认 → 安装重启链路符合
  "不自动静默安装"的契约（观察状态流转即可，不强制执行真实升级）。

## 5. 功能衔接检测

功能之间的衔接是最容易漏的验收点，逐项实际操作：

- [ ] 添加账户 → 面板立即出现新卡片 → 悬浮球小球列表同步出现。
- [ ] 移除账户 → 面板消失 → 悬浮球同步消失 → 设置中无残留。
- [ ] 切换主题 → 面板换肤 → 悬浮球皮肤同步切换 → 设置显示一致。
- [ ] 切换外观（浅色/深色/跟随系统）→ 面板与悬浮球同步；改系统外观时
  跟随系统模式实时响应。
- [ ] 修改昵称 → 面板账号名变化 → 悬浮球 tooltip / 账户名同步。
- [ ] 面板排序调整 → 重启 App 后顺序保持。
- [ ] 认证过期 → 健康状态与错误提示可见 → 重新授权后恢复。
- [ ] 单账户抓取失败 → 该卡片显示失败状态，其他账户不受影响。

## 6. 失败、恢复与持久化

- [ ] 零账户状态：空态引导正常，入口明确，不显示错误。
- [ ] 断网时打开面板：显示过期 / 失败状态，不伪装成正常数据。
- [ ] 平台限流 / 401 / 403 有可见错误归因，不是无限转圈。
- [ ] 快速重复点击托盘、刷新、主题切换不崩溃、不错乱。
- [ ] App 重启后：卡片顺序、昵称、主题、悬浮球位置与收起状态保持。
- [ ] 设置文件损坏或被清空时 App 能降级启动，不崩溃。

## 7. UI 视觉验收

视觉验收必须在真实 App 中完成，至少覆盖三套主题 × 浅色 / 深色，
并保留截图。悬浮球三套皮肤（Classic 胶囊 / Claude 书签 / Cyber 星球）
的大球与小球形态都要过目。

### 客观硬门槛

以下任一出现即可判定 `FAIL`：

- 卡片行结构（标签 / 重置时间 / 数值）漂移、截断、重叠或挤压换行；
- 套餐徽章色阶违反 `docs/07-theme-contract.md` 的六档语义；
- 健康色阶（绿→青→琥珀→红→深红）与使用比例不匹配；
- 余额行出现进度条，或额度行缺少进度条；
- 主值与主值对应那一档进度条没有同时出现；
- 任一主题 × 外观下文字对比度不可读、控件不可辨认；
- 380px 面板宽度 + 最坏字符串（长模型名 + "1 天 23 小时 59 分钟后重置"
  + 大余额）下布局损坏；
- 面板高度不自适应（内容少时留白过大或出现多余滚动区）；
- 悬浮球出现明显锯齿、错位、方块阴影或与主题不符的形态；
- 新界面明显偏离既有设计语言，且没有任务契约中的设计变更授权。

### 体验与审美检查

- [ ] 第一眼能识别主值、健康状态和套餐档位。
- [ ] 卡片间距、留白和视觉重心平衡，没有局部拥挤或大片无意义空白。
- [ ] 对齐线稳定：图标、名称、徽章、数值具有可解释的共同边界。
- [ ] 主操作（刷新、添加）与弱操作（查看详情）层级清楚。
- [ ] 与修改前截图并排比较，没有无意的视觉退化。
- [ ] 动画、加载和局部刷新不过度跳动。

当两个方案都符合契约、差异纯属风格偏好时，记录为 `DESIGN DECISION`，
由用户最终裁决；不得擅自按验收 Agent 的个人审美重构。

## 8. 性能与稳定性验收

- [ ] 冷启动到托盘可用的时间没有明显退化。
- [ ] 面板打开 / 关闭 / 滚动 / 切换视图无卡顿。
- [ ] 悬浮球拖动、吸附、展开 / 收起流畅，无掉帧、残影。
- [ ] 常驻内存实测（`ps` 或活动监视器）与改动前对比无显著增长。
- [ ] 长时间运行（至少覆盖一个完整刷新周期）无内存无界增长。
- [ ] 崩溃或卡死可以通过日志、采样或最小步骤稳定定位；不能只写"偶现"。

## 9. 双端差异与发布

- [ ] macOS：菜单栏定位、失焦关闭、Dock 隐藏、多显示器行为正确。
- [ ] Windows（实机）：任务栏无窗口、不抢焦点、安装卸载正常——未经实机
  冒烟标 `BLOCKED`，不得凭代码判定 `PASS`。
- [ ] 自动更新在两端的行为符合各自平台契约。
- [ ] 发布验收：CI 三端全绿 + `latest.json` 三平台 + 至少 macOS 一端
  完成"下载 → 安装 → 运行 → 核心功能"的真实验证。

## 10. 模块回归

- [ ] 已执行 `module-checklists.md` 中本轮目标模块的全部适用体验项。
- [ ] 已执行至少一个上游入口和一个下游结果模块（如改 Provider 映射，
  上游验收添加向导、下游验收面板卡片与悬浮球）。
- [ ] 修复旧回退时，已对照功能契约、历史截图或已确认版本。
- [ ] 没有要求用户凭记忆逐项寻找丢失功能。

```text
场景结果：
- [PASS/FAIL/BLOCKED/N/A] <场景ID与名称>
  步骤：<真实操作>
  预期 / 实际：<差异>
  证据：<截图、日志、设置文件>

体验发现：
- [P0-P3 / DESIGN DECISION] <标题>
  位置：<页面或控件>
  规则 / 基准：<契约、主题条目或任务契约>
  复现：<最短步骤>
  证据：<主题 × 外观对照截图>
  复验：<修复后检查范围>

衔接检测：<执行的功能衔接项与结果>
相邻回归：<执行的模块清单ID与结果>
未执行项目：<原因和残余风险>

```

存在未处理 P0 / P1 时结论必须为"不通过"。视觉硬门槛失败属于真实验收
失败；`DESIGN DECISION` 只有在方案均符合既有契约时才使用。
