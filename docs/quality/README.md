# TokenMeter 质量体系

本目录把项目质量要求转换为可以逐项执行、留证和复验的清单。根目录 `AGENTS.md`
规定设计原则与强制边界，本目录规定每个阶段具体检查什么、谁来检查、
什么叫通过。

## 固定角色

TokenMeter 默认只设三个 Agent 角色，检查维度不再各自创建常驻 Agent。

### 主开发 Agent

- 还原需求、编写任务契约并确定风险等级。
- 负责全部产品代码修改、冲突处理和最终整合。
- 完成局部验证（`tsc`、`cargo test`、`dev-deploy.sh` 实测），处理审核与验收发现。
- 未取得用户对应授权时，不提交、推送、部署或发布。

### 独立审核 Agent

- 对仓库保持只读。
- 开发前检查架构边界、契约兼容、影响范围和回退风险。
- 开发后检查 diff、代码质量、契约一致性、安全、性能和测试设计。
- 根据任务风险选择审核维度；任何"不适用"都要说明原因。
- 发现问题后只提交报告，不顺手修改产品代码。

### 最终验收 Agent

- 不参与实现，以原始需求和任务契约为准，站在最终用户角度。
- 构建、部署并确认运行的是本轮产物（进程路径、版本号核对）。
- 对真实运行的 App 做黑盒操作：点击托盘、拖动悬浮球、切换主题、
  走完添加供应商流程，检查功能实现、功能间衔接、异常路径和旧功能回归。
- 界面美观度与合规性由验收 Agent 按客观门槛直接判定（见下文）。
- 对仓库保持只读；截图、日志和测试配置写入隔离目录
  （`TOKENMETER_DATA_DIR` 隔离或 `dev-deploy.sh --isolate`）。
- 验收失败后由主开发 Agent 修复，再对原失败路径和相邻路径复验。

## 文件结构

| 文件 | 用途 | 主要使用者 |
| --- | --- | --- |
| `task-contract-template.md` | 每轮任务的范围、风险和可观察验收标准 | 主开发 Agent |
| `review-checklist.md` | 架构、契约、代码、安全和测试审核 | 独立审核 Agent |
| `acceptance-checklist.md` | 真实 App 功能、衔接、UI、稳定性与回归验收 | 最终验收 Agent |
| `module-checklists.md` | 16 个产品模块不能丢失的技术和体验基线 | 三类 Agent |
| `agent-prompts.md` | 主 Agent 向独立审核 / 验收 Agent 交接的标准 Prompt | 主开发 Agent |

现有专项契约继续有效：

- 项目规约：`../../AGENTS.md`
- 平台接口调研：`../01-provider-matrix.md`
- 架构与分层：`../03-architecture.md`、`../04-three-layer.md`
- 卡片契约：`../05-provider-card-contract.md`
- 主题契约：`../07-theme-contract.md`

专项契约与本目录冲突时，先记录冲突；安全、凭证完整性和用户已依赖行为
采用更严格的一项，最终由主开发 Agent 提请用户确认产品取舍。

## 风险等级

| 等级 | 定义 | 流程要求 |
| --- | --- | --- |
| `R0` | 纯文档、素材、注释，不改任何行为 | 主开发自验即可 |
| `R1` | 局部 UI 文案/样式，不涉及契约与数据 | 主开发自验 + 关键截图 |
| `R2` | 功能变更、新供应商、主题/悬浮球/设置变更 | 独立审核 + 真实 App 验收 |
| `R3` | 凭证、删除、自动更新、发布、OAuth、多平台窗口行为 | 独立审核（全维度）+ 真实 App 验收 + 复验 |

## 标准流程

1. 主开发 Agent 从原始需求编写任务契约，列出非目标、风险和相邻回归范围。
2. `R2` / `R3` 任务由独立审核 Agent 做实现前检查；`R0` / `R1` 可简化。
3. 主开发 Agent 实现并完成最相关的自动验证与本机实测。
4. 独立审核 Agent 按 `review-checklist.md` 和相关模块清单审核固定 diff。
5. `R2` / `R3` 任务由最终验收 Agent 按 `acceptance-checklist.md` 操作真实 App。
6. 主开发 Agent 修复发现；原审核或验收 Agent 复验失败路径及相邻回归路径。
7. 所有强制门槛通过后，才可根据用户授权提交、推送、部署或发布。

## 清单结果

每个适用检查项只能使用以下结果：

- `PASS`：已经执行并有证据。
- `FAIL`：实际结果不符合要求，附严重度、复现和证据。
- `BLOCKED`：受环境、账号、设备或授权阻挡，说明残余风险。
- `N/A`：确实不适用，必须写原因。

未填写、未执行或"看起来应该没问题"不能算 `PASS`。`BLOCKED` 是否可以
交付由任务风险和用户明确接受决定，主开发 Agent 不能自行降级。

## UI 好不好看的判定权

最终验收 Agent 可以并且必须判定可证实的视觉质量问题，包括：

- 是否违反主题契约的槽位、字号层级、健康色阶和套餐色阶语义；
- 卡片行结构（标签 / 重置时间 / 数值）是否漂移、截断、重叠、挤压换行；
- 三套主题 × 明暗外观 × 悬浮球皮肤是否全部生效且可读；
- 380px 面板宽度与最坏字符串（长模型名 + 长倒计时 + 大数值）下是否稳定；
- 新界面是否明显偏离已有产品截图和既有设计语言。

这些问题有契约或对照证据，验收 Agent 可以直接判定 `FAIL`，不需要等待
用户指出"很丑"。

以下情况属于产品审美或方向选择，验收 Agent 只能标记为 `DESIGN DECISION`，
由用户作为产品负责人最终决定：

- 两个方案都符合契约，但风格偏好不同；
- 是否采用新的视觉语言、新主题或大范围布局调整；
- "更精致""更科技感"等缺少既有基准的主观目标。

主开发 Agent 不得以"审美主观"为由忽略明确的契约违例；验收 Agent 也不得
用个人喜好推翻已经确认的设计方向。

## 证据最低要求

- 代码结论：文件、符号、base / head、测试命令和结果。
- 数据结论：隔离数据目录、变更前后设置文件状态；禁止用真实凭证库做破坏性测试。
- UI 结论：App 路径与版本、操作步骤、主题 × 外观和必要截图。
- 网络结论：请求结果、错误归因、限流影响和账号安全（测试请求频率克制）。
- 发布结论：提交 SHA、CI 运行、三端产物、`latest.json` 三平台校验和
  真实安装运行验证。

清单是最低要求，不限制审核或验收 Agent 针对本轮改动追加探索性检查。
