# 用量数据小数精度调研

> 调研日期：2026-08-02 · 来源：各平台官方/实测 API 响应样本（见 `docs/01-provider-matrix.md`）

## 结论

返回的用量/余额数据中，**金额类普遍带小数（2–5 位），百分比类样本为整数但需按 1 位小数防御，Token 数为整数**。

| 平台 / 字段 | 样本值 | 小数位 | 类型 | 显示建议 |
|---|---|---|---|---|
| **Moonshot** 余额 `available_balance` | `49.58894` | **5 位** | 金额(CNY/USD) | 内部 f64 全精度；显示四舍五入 2 位（`¥49.59`），或按偏好 4 位 |
| **Moonshot** `voucher_balance` / `cash_balance` | `46.58893` / `3.00001` | 5 位 | 金额 | 同上 |
| **DeepSeek** `total_balance` 等 | `"110.00"`（字符串） | 2 位 | 金额(CNY) | 解析为 f64，显示 2 位 |
| **OpenAI** credits `balance` | `5.39` | 2 位 | 金额(USD) | 显示 2 位 |
| **腾讯** `DescribeAccountBalance` | 元，带小数 | 2+ 位 | 金额 | 显示 2 位 |
| **OpenAI Codex** `used_percent` | `6` / `24` / `0` | 整数 | 百分比 | 计算值可能含小数 → 显示 1 位（`26.0%`） |
| **Kimi Code** `limit` / `remaining` | `"100"` / `"74"`（字符串） | 整数 | 计数 | 用 `1 - remaining/limit` 算 %，显示 1 位 |
| **腾讯 Token Plan** 额度包余量 | 整数 token | 整数 | 计数 | 比例 `剩余/总额` 显示 1 位小数 |
| **Token 数**（DeepSeek 逆向 / 腾讯 `TotalToken` 等） | 整数 | 0 位 | 计数 | 千分位格式化（`3.1M`），无小数 |

## 关键风险

1. **Moonshot 返回 5 位小数** —— Rust 侧 `serde` 必须用 `f64` 解析，不能用 `i64`/`u64`，否则 `49.58894` 直接丢精度。
2. **DeepSeek / 腾讯余额是字符串**（`"110.00"`），需要先 `trim` 再 `parse::<f64>()`，不能直接当数字。
3. **百分比类字段官方样本是整数**，但本 App 的「消耗%」多为本地计算值（如余额差分、Kimi `remaining/limit`），可能非整数 —— 一律按 1 位小数格式化，避免 `26%` 误显掩盖 `26.4%` 的紧张度差异。

## 格式化工具建议（前端 + Rust 共享规则）

```
fmtMoney(v: f64, cur: "¥"|"$") -> 2 位小数，千分位
fmtPct(v: f64)   -> 1 位小数 + "%"（如 26.0% / 15.5%）
fmtTok(v: f64)   -> 整数 + 单位（M/K），如 3.1M
```

Rust 侧 `serde` 解析余额字段统一用 `f64`；前端 `Intl.NumberFormat` 或自写 `toFixed` 即可。

## 对 UI 的影响

- 余额 hero 数字、消耗明细金额：原预览已用 2 位小数（`184.52` / `¥12.40`），与结论一致。
- 进度条百分比（`wrow-pct`）：改为 1 位小数显示（`82.0%` 而非 `82%`），更诚实反映计算值。
- 不强制改后端，仅明确解析类型（f64）与显示精度。
